面试题汇总 如何保证缓存的双写一致性？ 缓存的双写一致性很难保证强一致，只能尽可能降低不一致的概率，确保最终一致。我们项目中采用的是Cache Aside模式。简单来说就是在更新数据库之后删除缓存；在查询时先查询缓存，如果未命中则查询数据库并写入缓存。同时我们会给缓存设置过期时间作为兜底方案。如果真的出现了不一致的情况，也可以通过缓存过期来保证最终一致。 为什么不采用延迟双删机制？ 延迟双删的第一次删除并没有实际意义，第二次采用删除删除主要是解决数据库主从同步的延迟问题，我认为这是数据库主从的一致性问题，与缓存同步无关。既然主节点数据已经更新，Redis的缓存也应该更新。而且延迟双删会增加缓存业务的复杂度，也没能完全避免缓存一致性问题（延时时间的不确定性）。 延迟双删： 删除缓存：首先执行删除缓存的操作 更新数据库：然后执行更新数据库的操作 延时等待：在删除缓存之后，等待一段时间，避免更新数据库期间的脏数据被写入到缓存，这个时间可以根据业务读取平均耗时来设置 再次删除缓存：等待时间结束后，再次执行删除缓存的操作 为什么不先删除缓存再更新数据库？ 因为删除缓存到数据库更新完成之间存在一个时间窗口，其他线程可能会读取旧数据并重新写入缓存，从而导致长期不一致。 误区：Cache Aside模式写操作不会主动更新缓存，读操作没有命中缓存才会写入缓存，这是一个懒加载 描述一下redis的雪崩问题，如何解决？ 缓存雪崩的常见原因有两个，第一是因为大量的key同时过时。针对这个问题我们可以给缓存key设置不同的TTL值（随机），避免key同时过期。 第二个原因是Redis宕机导致缓存不可用。针对这个问题我们可以用集群提高Redis的可用性。也可以添加多级缓存，当Redis宕机时还有本地缓存的可用。 描述一下redis的穿透问题，如何解决？ 缓存穿透也可以说是穿透攻击，具体来说就是因为请求访问到了数据库不存在的值，这样缓存无法命中，必然访问数据库。如果高并发的访问这样的接口，会给数据库带来巨大压力。 我们项目中是基于布隆过滤器来解决缓存穿透问题的，当缓存未命中时，基于布隆过滤器判断数据是否存在。如果不存在则不去访问数据库。 当然也可以缓存空值来解决，不过这种方案比较浪费内存 用户请求的数据在缓存中和数据库都不存在，不断发出请求，给数据库带来巨大压力 解决方案 缓存null值 布隆过滤 做好数据的基础格式校验 加强用户权限校验 做好热点参数的限流 对某个访问频率异常高的参数值进行单独限流，防止缓存穿透请求持续冲击数据库 生产环境中的组合方案（请求→参数校验→布隆过滤器→Redis缓存→热点参数限流→数据库） 描述一下redis的击穿问题，如何解决？ 缓存击穿往往是热点Key引起的，当热点Key过期时，大量请求涌入同时查询，发现缓存未命中都会去访问数据库，导致数据库压力激增。 解决这个问题的主要思路就是避免多线程并发去重建缓存。因此方案有两种。 第一种是基于互斥锁，当发现缓存未命中时需要先获取互斥锁，再重建缓存，缓存重建完成释放锁。这样就可用保证缓存重建同一时刻只有一个线程执行。不过这种做法会导致缓存重建时的性能严重下降。 第二种是基于逻辑过期，也就是不给热点Key设置过期时间而是给数据添加一个过期时间的字段。这样热点Key就不会过期，缓存中永远有数据。 查询到数据时基于其中的过期时间判断key是否过期，如果过期开启新线程异步重建缓存，而查询请求先返回旧数据即可。当然这个过程也要加互斥锁，但由于重建缓存是异步的。而且获取锁失败也无需等待，而是返回旧数据，这样性能几乎不受影响。 无论采用哪种方式，在获取互斥锁后一定要再次判断缓存是否命中，做double check，因为当你获取锁成功时，可能在你之前有其他线程已经重建缓存了。 主从集群主要解决读写分离和数据冗余问题，提高读性能和数据安全性；哨兵集群是在主从基础上解决高可用问题，通过监控和自动故障转移保证主节点宕机时服务不中断。 Redis的单线程还是多线程？如果都是的话，怎么理解？ Redis 核心数据操作是单线程的，利用事件循环和 IO 多路复用保证命令原子性和高性能。但从 Redis 6 开始，网络 I/O、持久化等操作可以多线程执行，用来提升吞吐量，因此可以说 Redis 既是单线程又是多线程，需要区分核心操作和后台任务。 Redis有哪些持久化方式？怎么配置？ Redis 支持 RDB（快照）、AOF（操作日志）和混合持久化。RDB 性能高，适合备份；AOF 数据安全性高，支持重放；混合模式兼顾启动速度和数据安全。可以通过 redis.conf 配置快照策略、AOF 同步方式和文件路径。 redis中怎么解决分片集群中的数据倾斜问题？ Redis 分片集群的数据倾斜是指某些节点数据或请求过多，形成热点。解决方法有四点： 一是保证 hash slot 均匀分布，必要时迁移 slot； 二是用哈希标签合理分组 key，避免热点集中； 三是对热点 key 做拆分、复制或本地/多级缓存，分流请求压力； 四是监控节点负载，动态迁移热点 slot 或增加节点。 核心思想就是 均衡存储 + 分流请求 + 热点拆分 + 动态调节。 Redis的SortedSet的底层数据结构是怎样的？ SortedSet是有序集合，底层存储的每个数据都包含element和score两个值。score是得分，element是字符串。SortedSet会根据每个element的score值排序，形成有序集合。 它支持很多操作，比如： 根据element查询score值 按照score值升序或降序查询element 要实现根据element查询对应的score值，就必须实现element与score之间的键值映射。SortedSet底层是基于HashTable来实现的。 要实现对score值排序，并且查询效率还高，就需要有一种高效的有序数据结构。SortedSet是基于跳表实现的。 因为SortedSet底层需要用到两种数据结构，对内存占用比较高。因此Redis底层会对SortedSet中的元素大小做判断。如果元素大小小于128，并且每个元素都小于64字节，SortedSet底层会采用ZipList，也就是压缩列表来代替HashTable和SkipList 因为ZipList存在连锁更新问题，因此在Redis 7.0以后，ZipList又被替换为Listpack（紧凑列表）
